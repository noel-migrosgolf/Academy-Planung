# AI Academy Golf – Planung

Planungstool für die AI Academy Golf im Golfpark Holzhäusern.

## Aufbau

- `server/` – Node.js/Express-Server mit API (Login, Benutzer, Pros, Kurse, Verlauf, KI)
- `public/` – Oberfläche (HTML/CSS/JS), Logo und Favicons unter `public/img/`
- PostgreSQL-Datenbank mit den Tabellen `users`, `sessions`, `pros`, `event_types`, `events`, `versions`, `ai_chats` und `settings`; das Schema wird beim Start automatisch angelegt bzw. ergänzt.

## Lokal starten

Voraussetzungen: Node.js 22+ und eine PostgreSQL-Datenbank.

```bash
cp .env.example .env   # Werte anpassen
npm install
npm run dev
```

Dann <http://localhost:3000> öffnen.

## Umgebungsvariablen

| Variable | Beschreibung |
|---|---|
| `DATABASE_URL` | Verbindungs-URL der PostgreSQL-Datenbank |
| `ADMIN_PASSWORD` | Passwort für den Admin-Bereich |
| `DATABASE_SSL` | `true`, wenn die Datenbank SSL verlangt (z. B. externe Render-URL) |
| `EXPORT_TOKEN` | Optional: Schlüssel für den Lesezugriff auf `GET /api/export` ohne Anmeldung (Header `X-Export-Token`) |
| `API_TOKEN` | Optional: Schlüssel für die Datenpflege über die API (Header `X-Api-Token`). Darf Pros, Kurstypen, Kurse und den Verlauf bearbeiten, aber keine Benutzerkonten. Löschen der Variable sperrt den Zugang sofort. |
| `ANTHROPIC_API_KEY` | Schlüssel für den KI-Assistenten (console.anthropic.com). Ohne ihn ist der Reiter KI sichtbar, aber gesperrt. |
| `ANTHROPIC_WORKSPACE_ID` | Nur nötig, wenn der Schlüssel keinem Workspace zugeordnet ist: ID des Workspace (Console → Settings → Workspaces, beginnt mit `wrkspc_`) |
| `AI_MODEL` | Optional: Modell der KI, Standard `claude-opus-5-5` (günstiger: `claude-sonnet-5-5`) |
| `AI_EFFORT` | Optional: Denkaufwand `low` (Standard, spart Tokens), `medium` oder `high` |
| `AI_FALLBACKS` | Optional: `off` schaltet das Ausweichmodell bei abgelehnten Anfragen aus |
| `NODE_ENV` | `production` auf dem Server (sichere Cookies) |

## Aktueller Stand

- **Login** wie im Event Manager: Benutzer wählen, Passwort eingeben, Ladeanimation und Begrüssung (Passwörter als scrypt-Hash in der Datenbank). Benutzer mit Admin-Rechten melden sich normal an; zusätzlich gibt es oben rechts den Notzugang mit dem Admin-Passwort (`ADMIN_PASSWORD`).
- **Pläne** (`server/plans.js`, `public/js/plans.js`): Jeder Benutzer hat eigene Pläne (beim ersten Anmelden wird «Mein Plan» angelegt) und kann weitere anlegen, auch als Kopie des aktuellen Plans (Termine und Regeln). Termine, Regeln, Verlauf und KI-Chats gehören zum Plan; Pros und Kurstypen sind gemeinsam. Der Besitzer teilt einen Plan pro Person mit «darf ansehen» oder «darf bearbeiten». Admins (und der API-Schlüssel) sehen und bearbeiten alle Pläne. Oben rechts wählt man den Plan; die Anfragen tragen ihn im Header `X-Plan-Id` (API ohne Header: Hauptplan). Die bisherigen Daten bilden Noels «Hauptplan». Überschneidungen, Maxima und Regeln gelten je Plan.
- **Kalender** (`public/js/planner.js`): Einsatzkalender der Pros mit den Ansichten Tag, Woche, Monat und Saison, Navigation per Datum und KW, Filter nach Pros und Umschalter Brutto/Netto für alle Stundensummen. In der Tagesansicht entstehen Kurse durch Aufziehen eines Zeitraums oder per Klick (1 h); Klick auf einen Kurs öffnet ihn zum Bearbeiten. Rechtsklick (Tag, Woche, Monat, Kurse-Liste) öffnet ein Menü: auf einer freien Stelle «Kurs erstellen» mit vorausgefülltem Pro, Datum und nächster freier Stunde, auf einem Kurs «Bearbeiten» und «Löschen».
- **Kurse** (`public/js/events.js`): Kurstypen verwalten (mit frei wählbarer, eindeutiger ID wie «PR2A», von Admins änderbar; KI und API finden Typen auch per ID). Jeder Typ hat einen Einsatzbereich (Kurse – dazu gehört auch der Einzelunterricht –, Bambini, GCE oder alle Pros); nur Pros mit diesem Bereich lassen sich einteilen (Dialog, API, KI und automatisches Auslasten). Die Typenliste lässt sich nach Bereich filtern. Pro Typ lässt sich ausserdem einstellen, wann er einplanbar ist (von–bis; alle Termine einer Serie müssen hineinfallen) und wie viele Sollstunden (brutto) er höchstens umfassen darf, über alle Pros zusammen; beides gilt überall, auch beim Auslasten und Kurse planen (Typ, Pro, Datum, Zeit, Notiz). Unter «Darf nicht parallel stattfinden zu» wählt man andere Kurstypen (Dropdown mit Häkchen); deren Termine dürfen sich im selben Plan zeitlich nicht überschneiden (belegte Zeit inkl. Puffer), auch nicht bei verschiedenen Pros. Die Einstellung gilt gegenseitig und wird beim Partner automatisch mit eingetragen; Dialog, API, KI und Auslasten halten sie ein. Gibt es beim Speichern schon Überschneidungen, bleiben diese bestehen und werden als Hinweis gemeldet. Der Reiter **Geplante Kurse** listet alle Kurse mit Brutto/Netto. Kurstypen legen nur Admins an. Brutto und Netto werden pro 30 min geplanter Zeit angegeben, z. B. Einzelstunde 30/25 → 1 h = 1 h brutto (zählt gegen die Sollstunden) = 50 min netto. Der Unterricht beginnt pünktlich, der Puffer liegt gesammelt am Ende (09:00–09:50 Unterricht, 09:50–10:00 Puffer). Überschneidungen beim selben Pro werden abgelehnt. Kurstypen können ausserdem pauschale Stunden pro Termin, eine feste Uhrzeit, einen festen Wochentag für den ersten Termin und eine Serie von Terminen haben (Abstände in Tagen). Beispiel «Platzreife Teil 1 A»: 4 Termine Sa, So, Sa, So, jeweils 10:00–12:30, pro Termin 3 h brutto und 2.5 h netto (Unterricht 10:00–12:30, Puffer 12:30–13:00, der Pro ist bis 13:00 belegt); beim Anlegen lässt sich unter «Erweitert» pro Termin ein anderer Pro wählen. Optional hat jeder Termin eine eigene Zeit («Zeit pro Termin», z. B. Platzreife Teil 2 A: Sa 14:00–16:30, So 10:00–12:30, So 14:00–16:30); dann sind auch mehrere Termine am selben Tag möglich (gleicher Abstand). Serien werden gemeinsam angelegt und gelöscht. Geplante Termine lassen sich im Pro, im Datum (verschieben) und in der Notiz ändern; die Zeit bleibt die des Termins. Pro und Datum gelten wahlweise nur für diesen Termin, für diesen und alle folgenden oder für alle Termine der Serie (`PUT /api/events/:id` mit `serie: "folgende"` bzw. `"alle"`; die Notiz gilt immer nur für den bearbeiteten Termin). Beim Verschieben ab einem Termin bzw. der ganzen Serie gelten wieder die Abstände der Serie (Schulferien werden übersprungen); ein einzeln verschobener Termin darf auch an einem anderen Wochentag liegen (Hinweis). Schon während der Eingabe prüft der Dialog per Probelauf (`dry_run: true`) alle betroffenen Termine und zeigt Kollisionen: Pro belegt (auch mit Terminen derselben Serie), Abwesenheit, Einsatzbereich, einplanbarer Zeitraum, Schulferien, «nicht parallel zu» und Regel-Obergrenzen. Mit Konflikten lässt sich nicht speichern.
- **Auslasten** (`public/js/autofill.js`, `POST /api/autofill`): Assistent in vier Schritten. 1) Art wählen: «Pros auslasten» oder «Einzelne Kurstypen nachplanen». 2) Kurstypen: beim Auslasten bis zu 10 Kurstypen priorisieren (Reihenfolge mit ↑/↓; sie werden der Reihe nach zuerst verteilt, je Serie an den passenden Pro mit der geringsten Auslastung im Verhältnis zum Ziel), danach füllen die übrigen gewählten Kurstypen bis zum Ziel auf (abschaltbar); beim Nachplanen Kurstypen anhaken und je die Anzahl Serien bzw. Einzeltermine angeben. 3) Ziel-Auslastung je Pro per Regler (Brutto in % der Sollstunden; beim Nachplanen die Obergrenze, ausser «Ziel darf überschritten werden»). 4) Zeitraum und Optionen (Regeln zuerst erfüllen, freie Tage beachten), «Vorschau» oder «Ausführen». Der Server verteilt gleichmässig über 2027, ohne Überschneidungen, nur im Einsatzbereich, ohne Abwesenheiten und unter Beachtung von Schulferien, «nicht parallel zu», Typ-Maxima und Regeln. Bestehende Kurse zählen mit, es wird nur ergänzt. Das Ergebnis zeigt je Kurstyp, wie viel verteilt wurde (und warum weniger, z. B. Maximum erreicht), und je Pro die neue Auslastung; es lässt sich direkt rückgängig machen. Admins speichern die Ziele dabei als Soll-Auslastung der Pros. «Alles entfernen» löscht alle Termine des aktuellen Plans im eingestellten Zeitraum (Bestätigung mit zweitem Klick, danach «Rückgängig» und ein Eintrag im Verlauf). API zusätzlich zu `ziele`, `typen`, `von`, `bis`: `prioritaet` (bis 10 Typen), `uebrige`, `nachplanen: [{ typ, anzahl }]`, `ziel_ueberschreiten`.
- **Regeln** (`server/rules.js`, `public/js/rules.js`): Regeln der Form «Zwischen Datum x und y müssen mindestens / genau / mehr als / höchstens z Sollstunden von Kurs k stattfinden» (Brutto-Stunden über alle Pros; jeder Termin zählt mit seinem Datum). Jede Regel zeigt live, ob sie erfüllt ist. «Genau» und «höchstens» sperren das Einplanen darüber hinaus (Dialog, API, KI, Auslasten); «Auslasten» füllt mit «Regeln zuerst erfüllen» fehlende Stunden auf, verteilt auf passende Pros mit der geringsten Auslastung. Zweite Regelart: «Mindestens x % der Sollstunden von Kursen … (Mehrfachauswahl) müssen an Wochentagen / am Wochenende / Mo, Di … stattfinden»; sie wird angezeigt und von «Auslasten» eingehalten (Termine an anderen Tagen nur, solange der Anteil nicht unter x % fällt), sperrt aber das Einplanen von Hand nicht. Dritte Regelart: «Kurse … finden nicht in den Schulferien des Kantons Zug statt» (Daten aus `public/js/ferien.js`, nur Ferien, keine Feiertage); Termine in den Ferien werden abgelehnt, Serien dieser Kurse überspringen Ferienwochen (die Termine rutschen um je eine Woche weiter), auch beim Auslasten. Jede Regel hat eine ID (R1, R2 …). «Warum?» bei einer Regel (bzw. `GET /api/rules/R3/check` oder das KI-Werkzeug «regel_pruefen») erklärt Stand, Verteilung, Hindernisse und Lösung. Nur Admins legen Regeln an; sie sind nicht im Verlauf.
- **Pros**: Übersicht mit Einstellungen je Pro (Kürzel, Sollstunden, Einsatzbereiche Kurse/Bambini/GCE, freie Tage, Soll-Auslastung, Abwesenheiten, Verfügbarkeitsregel). Pro Pro wird die Auslastung 2027 angezeigt: geplante Stunden (Summe der zugewiesenen Kurse, brutto) in Prozent der Sollstunden, mit Balken, Markierung der Soll-Auslastung und den offenen Stunden bis zum Ziel. Admins können Pros anlegen, bearbeiten und löschen. Startwerte in `server/pros.js`.
- **Schulferien** (`public/js/calendar.js`): Jahresübersicht 2027 mit den Schulferien und schulfreien Tagen des Kantons Zug (`public/js/ferien.js`).
- **Benutzer** (nur Admin): Benutzer anlegen und löschen, Admin-Rechte pro Benutzer vergeben oder entziehen (wirkt sofort).
- **Verlauf** (je Plan, `server/history.js`): Nach jeder Änderung an den Kursen (Zuweisungen: welcher Pro wann welchen Kurs hat) wird der Stand aller Kurse als Version gespeichert (mit Zeit, wer, was). «Wiederherstellen» setzt nur die Kurse zurück und ist selbst wieder eine Version. Pros, Kurstypen und Benutzerkonten werden manuell gepflegt, nicht gespeichert und beim Wiederherstellen nicht verändert (Kurse, deren Pro oder Typ es nicht mehr gibt, werden ausgelassen). Es werden die letzten 1000 Versionen behalten.
- **Export** (nur lesend): `GET /api/export` liefert Benutzer (ohne Passwörter), Pros, Kurstypen und Kurse als JSON. Admins nutzen den Button «Daten exportieren» auf der Benutzer-Seite; ohne Anmeldung nur mit Header `X-Export-Token`.
- **KI** (`server/ai.js`, `public/js/ai.js`): Chat mit Claude, der die Daten lesen und Kurse anlegen, ändern und löschen kann. Jede Änderung der KI wird als Version gespeichert und erscheint im Chat mit «Rückgängig». Das nimmt genau diese Änderung zurück (angelegte Kurse löschen, gelöschte wieder einfügen, geänderte auf die alten Werte setzen); alles andere, auch spätere Änderungen, bleibt unberührt. Gibt es einen Konflikt (z. B. inzwischen ein anderer Kurs zur selben Zeit), wird nichts geändert. Nur eine von der KI wiederhergestellte Version setzt beim Rückgängigmachen den ganzen Stand zurück. Die KI arbeitet im Hintergrund; der Chat zeigt laufend, was sie tut (auch nach einem Seitenwechsel). Für grosse Aufträge wie «alle Pros zu 65 % auslasten» nutzt sie das Werkzeug «auslasten»: der Server verteilt die Serien der gewählten Typen selbst gleichmässig über den Zeitraum, ohne Überschneidungen (optional unter Beachtung der freien Tage) – in Sekunden und mit wenigen Tokens. Admins pflegen unter «Regeln für die KI» die Planungsregeln; sie gelten für neu gestartete Chats. Tokensparend: knapper System-Prompt, Prompt-Caching, Werkzeuge mit kompakten Textzeilen statt JSON, Sammel-Aktionen, Denkaufwand `low`; bei langen Chats empfiehlt die Seite einen neuen Chat.
- **API für Planung** (mit Anmeldung oder `X-Api-Token`):
  - `GET /api/overview?from=YYYY-MM-DD&to=YYYY-MM-DD&pro=Name&format=text` – lesefreundliche Übersicht: Namen statt IDs, Zeiten als HH:MM, Stunden und Auslastung je Pro.
  - `POST /api/events/bulk` `{ events: [{ typ, pro, datum, von, bis, pros?, notiz? }], dry_run? }` – mehrere Kurse (auch Serien) in einem Aufruf.
  - `POST /api/events/bulk-update` `{ changes: [{ event_id, pro?, typ?, datum?, von?, bis?, notiz? }], dry_run? }`
  - `POST /api/events/bulk-delete` `{ ids: [...], serie?, dry_run? }`
  - Pros per Name oder Kürzel, Typen per Name, Zeiten als `HH:MM`. Jeder Aufruf gilt ganz oder gar nicht (bei Fehlern 409 und nichts geändert) und ergibt genau eine Version im Verlauf. `dry_run: true` prüft nur.
